## Map #1

## Destination

All of Open WebUI's agentic chat runs on pi: a Node sidecar hosts pi's agent loop for every chat; every OWUI capability reaches the agent as a bridged tool; OWUI's chat UI and its rendering/streaming pipeline keep working unchanged; execution happens only on the machine the user selected, never on another host by mistake. The agent is self-learning within guards: it learns from its own mistakes, improves its own skills, and creates and fixes its own tools, with no swarm of reviewers.

## Notes

Domain: Open WebUI v0.12.3 (FastAPI backend under `backend/open_webui` + Svelte frontend), replacing its Python agent loop (`backend/open_webui/utils/middleware.py`) with pi's agent core (`pi-agent-core` / `pi-ai`, TypeScript).

Decisions locked in the charting session:
- **Engine**: pi is the *only* loop, full replacement of the Python pipeline.
- **Features are bridged INTO pi as tools**; code-mode enabled as the orchestration layer; exposure balance decided by the tool-bridge ticket: code-mode `on`, everyday spine direct, big inventories deferred.
- **Memory**: OWUI's store stays the source of truth, bridged as tools + context injection; mutating memory tools bridge **unguarded** — ownership scoping only (human decision in the tool-bridge ticket, overriding this charting-session note; `MUTATING_MEMORY_TOOLS` dies with the Python loop).
- **Machines**: pi sees and executes on the selected tool-server machine only; strict isolation is a hard requirement, never a nicety.
- **Architecture**: sidecar Node service (e.g. `backend/pi-agent`), HTTP/SSE between OWUI backend and sidecar, 1:1 chat ↔ pi-session.
- **Tracker**: GitHub issues on this repo — see `docs/agents/issue-tracker.md`.
- **Style**: standing preference for the whole effort — every ticket and every session works in poteto style. Do all implementation and all code fact-finding via `poteto-mode` (read `/poteto-mode` SKILL.md, plus any principle leaf it triggers, before acting). Applies to the whole project, not just this map.

Skills every session should consult: read `GLOSSARY.md` and `docs/adr/` per `docs/agents/domain.md`; use the research skill for external facts.

Standing preference — snapshot durability: the map and its tickets are committed to git as a backup after every change. After any edit to the map body or any ticket, run `docs/agents/tracker-snapshot.sh` (lives on the \`tracker/snapshot\` branch) and commit the regenerated \`docs/agents/tracker-snapshot.md\` to that branch, then push. Read the snapshot only when the tracker is unavailable; GitHub issues stay the canonical copy.

Standing preference — plain language, everywhere: all communication with the human and all prose written into the repo (tickets, specs, comments, docs, code) must read like one person talking plainly to another. No jargon, no shorthand, no walls of linked numbers. If a technical term carries real weight (a glossary term, a package name), say it once and explain it in everyday words next to it. Applies to replies, narration, and code comments alike; for tickets in particular, prefer short sentences a non-engineer could follow.

## Decisions so far

- [How do you embed pi's agent loop in a host application](https://github.com/LiveSparks/open-webui/issues/3): embed the pi-coding-agent SDK in-process (`createAgentSession` + `session.subscribe`/`prompt`); `agent_settled` ends the stream; `SessionManager` gives 1:1 chat↔session, resume/fork; `customTools` for bridges; OWUI keeps credential authority via `ModelRuntime`.
- [What chat events does Open WebUI's frontend consume during a response](https://github.com/LiveSparks/open-webui/issues/4): Socket.IO `events` envelope only; content as `chat:completion` Responses-style `output` items with delta frames; inventory covers status/citations/files/errors/approvals; DB persistence, Redis snapshots, task registry + throttle params are loop-owned and must be ported.
- [How do OWUI tool servers expose a selected machine to the agent](https://github.com/LiveSparks/open-webui/issues/5): machine = server-resolved opaque connection id from chat metadata; auth/context headers injected server-side; executor surface = `execute_tool_server` (`run_command`, `files/read`, `write_file`, …); isolation is structural — id never model-controlled.
- [Which Open WebUI features must work through pi on day one](https://github.com/LiveSparks/open-webui/issues/2): must = spine (streaming + event protocol, tool loop for functions/MCP/tool servers, approvals), RAG/files/web-search/memory (pre-loop, S), image gen, voice (not realtime), pipelines inlet/outlet, title/tags/follow-ups, structured outputs; code execution mandatory with source decided in the new conditional ticket; fall back = stream filters, loop-result images, autocomplete/MOA; verify-only = automations, timers, channels, admin/observability; out of scope = realtime voice call.
- [Tool bridge: how OWUI capabilities become pi tools](https://github.com/LiveSparks/open-webui/issues/7): one loopback MCP server hosted in OWUI FastAPI, consumed per-session via `createMcpExtension({loadConfig})`; backend stays tool authority; phase-1 set = memory + KB + chat files + web + image + execute_code + Tools DB + MCP relay (terminals → #8); code-mode `on` with spine direct / inventory deferred; RAG & memory context injection stay pre-loop Python; mutating memory tools bridge unguarded (ownership only); auth via short-TTL signed session binding, credentials never leave OWUI.
- [Event bridge between pi's event stream and OWUI's chat pipeline](https://github.com/LiveSparks/open-webui/issues/6): sidecar emits pi-native SSE; FastAPI translates into the Socket.IO `events` envelope so DB/Redis/task-registry stay loop-owned Python; sidecar stateless toward OWUI storage; stop → `abort()` + `{done:true}`; steering replaces interrupt for send-during-generation (accepted UI change); edit-resend → session fork/restore; phase-1 niceties match the day-one tier incl. approvals, `request:user_input`, pipelines inlet/outlet; `auto_retry_*` → status pill, terminal failure → `chat:message:error` + done.
- [Binding pi's local tools to the selected machine with strict isolation](https://github.com/LiveSparks/open-webui/issues/8): pi's built-ins (`bash`, `read`, `edit`, `write`) rebind per-session to the machine via pi's operations seams, passed as `customTools`; calls route sidecar → OWUI backend loopback executor → `execute_tool_server`, so the sidecar never learns a machine URL or key; no machine → tools absent (fail closed); session cwd is a per-chat directory on the machine; one machine at a time, re-resolved per turn by the backend; phase 1 = admin-configured machines only; nothing agent-facing stays sidecar-local. Recorded in [ADR 0002](https://github.com/LiveSparks/open-webui/blob/main/docs/adr/0002-machine-binding.md).
- [Can the chat agent self-learn? harness2 and pi-continuous-learning mechanisms](https://github.com/LiveSparks/open-webui/issues/13): harness2 = offline researcher framework that rewrites an 8-component harness from rollout evidence with no reviewers — its guards (deterministic validation, evidence-lockdown, KEEP_BASE) and per-domain experience library (full adopted tree + edit rows + one grounded lesson) are the portable part, not its k-way recursion. pi-continuous-learning = working pi extension pipeline: observe events to JSONL, async cheap-model analyzer reflects into instinct lessons with a numeric confidence ledger and zero-cost dedup/contradiction guards, injects before each turn, feeds outcomes back, graduates mature lessons into AGENTS.md/SKILL.md. Sidecar shape: pcl's loop over workspace DB + harness2's validator as the reviewer-swarm replacement.
- [Session lifecycle and sidecar deployment shape](https://github.com/LiveSparks/open-webui/issues/9): one shared backend-owned sidecar process; pi session created lazily on first message, id stored on the chat record; session files under `DATA_DIR`; crash mid-generation = error for that turn, resume next message (hardening via pi-durable tracked separately); one active run per session, steering for races, signed binding re-minted per turn, env-var config with version handshake, sidecar bundled in the OWUI image with exact-pinned pi deps.
- [Can pi-durable host the sidecar's chat loop (bridge tools, MCP, steering, machine binding)](https://github.com/LiveSparks/open-webui/issues/16): custom TypeBox tools first-class; MCP consumption is the gap (needs a hand-rolled bridge, not a protocol blocker); steering, fork, abort, crash resume, compaction all supported; `ExecutionEnv` (HarnessOptions.env) seam fits the machine-binding decision; `watchEvents`/`watch()` fit the event bridge in SSE; SQLite (WAL, single file) recommended over JSONL; experimental churn bounded by exact-pinned lockstep deps.
- [Should the sidecar's chat loop run on pi-durable instead of the SDK session](https://github.com/LiveSparks/open-webui/issues/17): stay on the pi coding agent SDK; crash mid-generation = error for that turn, resume from JSONL on the next message; pi-durable not adopted (experimental, cannot consume the loopback MCP bridge, would revise #3/#6/#7); exact pinning + deliberate bumps stand; revisitable only if a later ticket needs a durable task runner.
- [Mapping OWUI's native sub-agents onto pi's loop](https://github.com/LiveSparks/open-webui/issues/10): `delegate_task` stays the tool contract; the sidecar spawns each delegation as a second in-process pi session (recursion banned, memory-mutating tools stripped, knobs OWUI-owned and fetched at delegation start); background children now inherit machine tools like foreground ones (deliberate change); live follow in both the delegation card and the child chat over one stream; enqueue-only steering from sub-agent views; new running-sub-agents card above the composer; background results return through the unchanged `process_pending_internal_messages` flow.
- [Code interpreter at day one: pi built-in vs bridged OWUI interpreter](https://github.com/LiveSparks/open-webui/issues/11): day-one code execution runs through bridged `execute_code` (direct exposure per the tool-bridge decision); the FastAPI translation special-cases its results into the native `open_webui:code_interpreter` item ("Analyzed" block, streamed code deltas, stdout/stderr/result, base64 image extraction); pi built-ins stay machine-bound and coexist, no phase-1 steering; a phase-1 system-prompt section tells the agent which execution surface it used, where it runs, and how isolated its effects are (new glossary term `execution surface`); pyodide rides on the bridge delivering the browser `execute:python` event-call, Jupyter otherwise; glossary change committed on branch `research/pi-durable-compat`.

- [Binding per-user direct tool-server connections to pi](https://github.com/LiveSparks/open-webui/issues/15): direct OpenAPI tools bridge day one with execution relayed to the user's browser over the existing Socket.IO event, keys browser-held; pi's built-ins never bind a browser-held connection (browser-relay route rejected as live-browser-only), relay failures translate the ordinary way, ownership per-user and context per-chat.

### Local patches to carry into implementation

The driving human keeps proven local fixes at `/root/owui-customizations` (patches, reapply runbook, audit scripts; written against the deployed 0.11.4 host). Both are confirmed wanted in the implementation run; facts below verified against this repo's 0.12.3 code.

1. **Per-chat terminal memory** (one feature across `patches/middleware.py.patch` + two frontend bundle patches). A saved chat remembers which terminal it used: the backend saves a changed terminal id on the chat record when a message arrives (with `touch=False` so sidebar ordering doesn't jump), the frontend writes the switch back through the ordinary chat-update API, and reopening a chat restores its terminal from the record, falling back to the last message's `meta.terminal_id`. Status in 0.12.3: still absent; restore comes from browser-global localStorage only (`src/routes/(app)/+layout.svelte:431`), `terminal_id` is recorded per message but never on the chat, and models can pin a scoped default terminal (`backend/open_webui/routers/models.py:950`, applied in `Chat.svelte:1232`). Home in the new design: the machine-binding story (chat remembers its machine, restored on open).
2. **Sync tool offload** (`patches/tools.py.patch`). Upstream runs plain-Python (non-async) tool functions directly on the event loop, so a tool that makes a blocking call back to the OWUI server itself deadlocks a single-worker uvicorn. The patch offloads sync tools to a worker thread (`asyncio.to_thread`). Status in 0.12.3: still broken (`backend/open_webui/utils/tools.py:319` runs sync tools on the loop; `backend/open_webui/utils/middleware.py:1134` awaits tool calls on the loop). Home in the new design: a guard the tool bridge must carry, since OWUI keeps executing bridged Python tools.
