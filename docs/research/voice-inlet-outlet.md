# Where voice and pipelines inlet/outlet sit against the pi sidecar

Research for the wayfinder map (Open WebUI × pi agent engine), answering [issue #24](https://github.com/LiveSparks/open-webui/issues/24). Facts for the verdict, not the verdict itself. Written from the working tree at `v0.12.3-2-g233ed5c66` (upstream 0.12.3, merge `91ea4e342`) and the resolved wayfinder tickets. Every claim names its source. Line numbers are from this tree.

## TL;DR verdicts

- **Voice. Covered by existing decisions.** The reading in the ticket is right. STT and TTS are plain HTTP endpoints in OWUI's Python, driven by the frontend before and after the loop. The two voice pieces that touch the model's context are pre-loop Python and already ride decisions that exist (issue #2 for the prompt injection, issue #7's prompt-head handoff for the transcript context). Nothing new to decide. One spec sentence is worth writing down at implementation time.
- **Pipelines inlet/outlet. A decision still to make.** Ticket #6 fixed where inlet and outlet run in the translation flow, but it never fixed the filter payload contract under pi-owned history. Today an inlet or outlet filter receives and can mutate the full request body, complete history included. Under the sidecar Python no longer assembles full history per turn, so both the inlet's visibility and the outlet's feedback path break open. Two decisions, both ticket-sized.

## Voice

### The endpoints never touch the loop

Speech-to-text is a backend HTTP endpoint, `POST /api/v1/audio/transcriptions` (`backend/open_webui/routers/audio/__init__.py:1456`). The frontend calls it directly in two places. Dictation records audio and sends the file for transcription, then puts the returned text into the message input (`src/lib/components/chat/MessageInput/VoiceRecording.svelte:196-216`). The call overlay transcribes each recorded turn and submits the text as an ordinary prompt (`src/lib/components/chat/MessageInput/CallOverlay.svelte:256-277`). A third STT engine, the browser's Web Speech API, never reaches the server at all (`VoiceRecording.svelte:191-193`).

Text-to-speech is the mirror image. `POST /api/v1/audio/speech` (`audio/__init__.py:762`) takes text and returns audio; the engines behind it are OpenAI, OpenAI realtime, ElevenLabs, Azure, transformers, and Mistral (`audio/__init__.py:437, 484, 604, 640, 676, 712`). The speak button on a reply and the response-auto-playback setting call it after the reply is done (`src/lib/components/chat/Messages/ResponseMessage.svelte:254`, `src/lib/components/chat/Chat.svelte:3524-3527`). During a live call the frontend splits the streaming reply into parts and synthesizes each part through the same endpoint (`Chat.svelte:2494-2531`, `CallOverlay.svelte:640-667`). The browser's `speechSynthesis` engine is again a no-server path. None of this reads or writes anything the agent loop produces beyond the finished message text the frontend already has.

The WebRTC realtime voice call lives separately in `backend/open_webui/routers/audio/realtime.py` and stays out of scope per issue #2, which calls the realtime voice call its own provider-side loop unrelated to the swap.

### What does touch the model's context, and why it is already decided

Two things in the loop's input are voice-specific, and both run pre-loop in Python.

First, the voice-mode system prompt. The frontend sets `features.voice: true` when the call overlay is active (`src/lib/components/chat/Chat.svelte:4110`). In `process_chat_payload` the backend injects the voice-mode template as a system message when that feature flag is set (`backend/open_webui/utils/middleware.py:2329-2340`; template config at `backend/open_webui/config.py:3252-3253`). Issue #2 already claimed this as a decision, calling dictation and articulation must-work by construction with no loop contact, and the voice-mode prompt injection a pre-loop item at weight S. Under the sidecar this injection happens on the Python side of the prompt-head handoff, the seam issue #7 fixed ("the assembled head of the prompt (system + injections) hands to the sidecar").

Second, historical spoken transcripts. When a reply is spoken aloud, the frontend saves the spoken text to the message's `meta.voice` through `POST /chats/{id}/messages/{message_id}` (`Chat.svelte:2398-2416`, backend form and persistence at `backend/open_webui/routers/chats.py:1489-1545`). On later turns `process_messages_with_output` reads `meta.voice.speech` from the DB and merges those transcripts into the message list sent to the model, marked as historical voice transcripts (`backend/open_webui/utils/middleware.py:1945-1990`). This is pre-loop context assembly like RAG and memory, and it crosses the same per-turn handoff that issue #7 established for prompt-head injections.

One spec point follows, and it is a consequence of decisions already made rather than a new fork. Because pi owns session history (edit-resend is a pi fork/restore then a fresh `prompt()`, per issue #6; the chat record carries the session id, per issue #9), Python stops assembling the full history per turn. The spoken-transcript merge must therefore ride the per-turn handoff as an injection item, sourced from OWUI's DB, instead of happening inside the full-history pass of `process_messages_with_output`. Say that explicitly in the implementation notes, and the day-one verify covers the rest. Issue #2 already lists "STT/TTS endpoints, admin analytics, evaluations: verify untouched."

## Pipelines inlet/outlet

### What ticket #6 already fixed

The resolution of [issue #6](https://github.com/LiveSparks/open-webui/issues/6) puts inlet/outlet on the phase-1 must-work list as "pipelines inlet/outlet as stream mutation points" and keeps DB persistence, Redis snapshots, and the `chat:active` registry loop-owned in Python. It also fixed the neighboring boundary. Stream-type filters are the one filter class that needs the loop, and they are deferred to phase 2. What it did not do is define what the inlet and outlet hooks receive and where their mutations land. The phrase "stream mutation points" is the only statement on that, and it is loose in both directions. Inlet today is not on the stream. Outlet is on the stream's end, not inside it.

### What 0.12.3 actually does

Inlet runs once, before any model call, on the assembled request. Two layers run in order inside `process_chat_payload`. Pipeline inlet filters POST the whole payload (`user` plus `body`, messages and metadata included) to each external pipeline server's `/filter/inlet` route and take the mutated payload back (`backend/open_webui/routers/pipelines.py:63-127`). Function inlet filters run the same shape locally. They get `body` plus injected params, and their return value replaces `form_data` (`backend/open_webui/utils/filter.py:135-136, 168-205`). The result feeds everything downstream, including the tool list (inlets can register tools that are merged later, `middleware.py:2454, 2921-2922`) and the feature-flag injections right after (`middleware.py:2336-2340`). An inlet error aborts the request (`middleware.py:2305-2308`).

Outlet runs once, after the response is complete. `outlet_filter_handler` is called inline at the end of every completion path (`middleware.py:4069, 4092, 6328`) with the final assistant message in `ctx['assistant_message']`. It rebuilds a body, runs pipeline outlet filters (`pipelines.py:129-180`) and function outlet filters, and then writes the mutated messages to the DB and emits `chat:outlet` so the frontend syncs (`middleware.py:3826-3890`). The OpenAI-compatible API path has its own outlet trigger behind `ENABLE_API_OUTLET_FILTERS` (`middleware.py:4083-4092`, `backend/open_webui/env.py:1060`), and the tasks router runs pipeline inlet filters on its own payloads for title and follow-up generation (`backend/open_webui/routers/tasks.py:202, 269, 334` and seven more call sites).

The load-bearing property in both cases is that the filter's `body` is the full request, and what comes back is the single source of truth for the request (inlet) or the persisted message and later turns (outlet).

### What breaks under the sidecar, and the two decisions left

Per turn, Python now hands the sidecar the prompt head plus injections and the new user message (issue #7), while pi's session owns the accumulated history (issue #6's edit-resend rule, issue #9's chat-to-session mapping). That removes the full-history body both filter types read and mutate today.

**Decision A, inlet's payload contract.** What do inlet filters see when Python no longer assembles history, and where do their mutations land? The workable shape is the one already implied by the handoff seam. Inlet runs in Python, before the sidecar's `prompt()` call, on a payload of head plus injections plus the new turn. Mutations to the system message and the current turn flow into the handoff. Mutations to historical messages have no target, because pi's session owns that history and a rewrite would mean a fork. That has to be chosen, and the choice has to name what a filter that today rewrites history (a redaction, a templating pass) gets instead. The anchor itself is nearly decided, so pin it in the same ticket rather than debate it. Inlet before `prompt()`, errors still fail the request, the tasks router keeps its own Python-side inlet calls since tasks never touch the loop (issue #2).

**Decision B, outlet's feedback path.** Outlet keeps its home. It runs in Python after the final translated frame arrives and before the DB persist, in the same spot `outlet_filter_handler` occupies today, and it keeps emitting `chat:outlet`. That part is fixed by issue #6's persistence ownership. The open part is a silent behavior change. Today an outlet mutation propagates into later turns, because the DB copy it writes is the history source. Under the sidecar pi's JSONL session keeps the unmutated reply, so the next turn's model context diverges from what the DB and the chat UI show. The decision is which of three worlds holds. Accept the divergence and define outlet as persistence-and-presentation-side only. Or feed the mutated reply back into pi's session through a session-rewrite path. Or have pi's next-turn context read the final assistant message from OWUI. Each has different costs, and issue #6 did not settle it.

Both decisions share one root, the filter payload contract at the sidecar seam, so they fit one ticket with two named calls. A ticket named something like "Inlet and outlet payload contract under pi-owned history" carries both, with Decision A first since Decision B's options depend on how the handoff shapes the body.
