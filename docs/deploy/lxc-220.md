# The .220 deployment box

Reference for the operator's live instance and the release path that feeds it.
Commissioned 2026-11-04. Facts only; the how-to lives in
`scripts/openwebui-pi/README.md`, the decisions in ADR 0007 and ADR 0008.

## The box

| Item | Value |
|---|---|
| Hostname / address | `openwebui-pi`, `192.168.18.220` |
| Web | `http://192.168.18.220:8080` (port 8080 from OWUI_PORT) |
| OS | Debian 12 LXC, unprivileged, 2 vCPU / modest RAM, ~15 GB disk |
| Install shape | ADR 0007 wheel: `open_webui-0.12.3` via `uv tool install`, launched by `/root/.local/bin/open-webui serve` (root) |
| Runtime deps | Node 22 (NodeSource; the sidecar needs ≥22.19), uv 0.6+ |
| Service | `/etc/systemd/system/open-webui.service` - simple, `Restart=on-failure`, Take over env from `/etc/openwebui-pi.env` |
| SSH | root with a password (kept in the orchestrate store, not in the repo) |

## State on disk

Everything worth keeping is under `DATA_DIR=/var/lib/open-webui`:

- `webui.db` - SQLite: chats, users, API keys, configs, agent lessons (the learning store reaches the same database through the backend's routers).
- `uploads/`, `vectordb/` - attachments and the RAG vector store.
- `pi-agent/` - the sidecar's agent dir (`auth.json`, `models.json` scratch; empty is fine).
- `pi_sessions/` - one pi JSONL per chat; restores imply nothing after a hard restart.
- `/var/backups/open-webui/data-<ts>/` - the updater's rollback copies (the five newest are kept). Restore requires a match with the migration state of the target wheel: only if the newer tree ran a DB migration serve.
- `/root/.webui_secret_key` - session-key file; survives every wheel swap; back up with the data.
- `/etc/openwebui-pi.env` - the configuration no wheel touches:
  `PI_WHEEL_URL` (currently pinned at `v0.12.3-pi.4`; switch back to `releases/latest/download/open_webui-0.12.3-py3-none-any.whl` for the moving pin), `OWUI_PORT=8080`, `AGENT_SIDECAR_PORT=8930`, `AGENT_SIDECAR_AGENT_DIR`, `AGENT_SIDECAR_MODEL=opencode-go/glm-5.3-flash`, `AGENT_SESSIONS`, `AGENT_LOOP_MODEL_IDS=glm-5.3-flash` (append composer model ids comma-separated), and `AGENT_LOOPBACK_URL=http://127.0.0.1:8080/loopback/mcp` (the minted bridge binding must be loopback; an external browser address must not become the URL).

## OpenCode connection

Admin Settings > Connections: base URL the sidecar catalog can match — `https://opencode.ai/zen/go/v1` (matching is now model-level; pi's pinned catalog carries the gateway per model). The API key stays in OWUI and crosses per turn through the short-TTL loopback route. Chat calls carry pi's own `x-opencode-session` (one chat = one pi session; compaction/summary side requests use separate routing ids by design). Chat Controls and the composer's `Effort` picker share `reasoning_effort` and are seeded: model param → the last level picked → the highest the model's ladder carries.

## Release and update path

1. Fix lands on `dev` (PR, not direct).
2. At a stable point, `dev` merges into `main` (only `main` gets a tag and only this merge reaches it).
3. Dispatch `.github/workflows/deploy-wheel.yml` (inputs: tag like `v0.12.3-pi.N`, optional `check_ref`, notes). It builds the wheel on Actions (never locally — standing order 20), asserts the packaged sidecar, and publishes the release with the IDENTICAL asset name. Releases so far: pi.1 (PR2-era), pi.2 (verified full program), pi.3 (catalog/matcher + front-end seed UI), pi.4 (auth marker + seeded effort + workspace ladder).
4. On the box: `openwebui-pi-update` — stops the service, backs up `DATA_DIR`, `uv tool install --force --refresh`, starts, waits for `/health`. `--refresh` is required: uv's wheel cache keys on the URL and the asset name stays constant across releases, so without it an update can install the previous release's bytes and still exit 0 (seen live during the pi.4 rollout).
5. Post-install sanity: `wc -c` the sidecar dist files against the wheel's content (index.js / providers.js grow when the sidecar changes), and `journalctl -u open-webui` for a `sidecar healthy` line. Keep the old `PI_WHEEL_URL` pin reachable for rollback.

## Housekeeping

- Builds: GitHub Actions only (standing order 20). The box never builds wheels, Docker images, or frontend bundles; local work runs lint/unit checks only, never two npm/build processes at once (standing order 14).
- Never block a reply on CI (standing order 21): dispatch, do other work, then query once per turn.
- A leftover `worker@swarm.local` commit appeared once in the dev lineage (content-equal to the PR 79 squash). origin/dev is verified clean (PR 78 → 79 → 80 lineage); retire any stale worker before it pushes again.
- Upstream workflows stay disabled by hand (backend.yaml, docker.yaml, frontend.yaml, release.yml, release-pypi.yml show `disabled_manually`); `deploy-wheel`, `pi-engine-verify` (dispatch-only), `issue-label`, and the PR-lane `regression` are the active surfaces.
